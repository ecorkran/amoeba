# Architecture: Runner & Routing Engine

## Overview

The Runner is the project's core artifact: a deterministic state machine that drives a project through its Context Forge (CF) / Squadron (SQ) lifecycle with zero discretion of its own. Its loop is the concept's: *while runnable work exists, issue a command, read what comes back, apply the routing table, and advance, send to the Judge, or write a blocked-state.* The routing engine is the table and the rule-application step inside that loop. Together they are the only part of Amoeba that **acts**: the substrate (100) stores and observes, the Judge (140) evaluates, the Translator (160) interprets, and the Runner is what turns state into the next command.

**The problem it addresses.** With 100 complete, Amoeba can remember everything and notice everything, and do nothing. A slice still advances only when a human runs `cf set`, launches `sq run`, reads the review, decides whether CONCERNS is acceptable, resumes a paused run, and does it again. Most of those decisions are mechanical. Squadron has since automated the *within-artifact* half (revise → review → gate loops inside one pipeline run) but stops at the run boundary: a run that cannot converge exits paused, and nothing picks it up, carries it across days, or decides what the next run should be.

**Scope.** This component owns: (1) the **Runner tenant**, hosted in the resident process beside the shipped tenants; (2) the **control surface**, the closed set of CF and SQ commands the Runner issues, each journaled before it runs and observed until it finishes; (3) the **lifecycle model**: how a project's CF plan and pointers become nodes in 100's tree, and what "runnable" means for each node kind; (4) **outcome ingestion**: turning a finished run's reviews, run state, and CF gate state into store records under 100's evidence rules; (5) the **routing engine**: tier inference, the routing table, and a recorded decision for every outcome; (6) the **intent vocabulary**: what an `intent` message may ask the Runner to do. It does **not** own consensus or judge invocation (140), natural-language interpretation or notification (160), within-artifact revise loops (Squadron's), or the store, inbox, feed, and observers it builds on (100).

**Motivation.** Everything before this initiative is plumbing for it, and everything after it (140, 160, 180) attaches to its decisions. It is also where the project's method lives: "build by inducing failure" edits the routing table, so the table has to be data, auditable, and the only place routing behavior is defined.

## Design Goals

- **Zero discretion, total auditability.** Every action the Runner takes is the output of a fixed rule over recorded inputs. Given the store's contents and the routing table version, any decision can be recomputed and explained after the fact: which rule fired, on which evidence.

- **Unattended between decisions that need a person.** A slice goes from "design pending" to "implemented and reviewed" without a human touching it, *unless* the routing table says a human is the next step. When it does, the Runner writes the blocked-state, moves on to other runnable work, and resumes the node when the resolution lands, hours or days later, across restarts.

- **Squadron does the work; the Runner decides what work is next.** The Runner never reimplements what a Squadron pipeline already does (generation, review, revise loops, gating inside a run). It chooses which pipeline runs on which node, and routes what the run returns.

- **One edit point for routing.** Changing which route a kind of outcome takes means editing the routing table and nothing else. Code defines a closed set of named inputs and predicates (what a "recurring finding" or a "vacuous check" is); the table alone decides what each combination of them does. No route is chosen in a code branch outside the table.

- **Many projects, one loop.** The Runner serves every project in the supervisor directory from one tenant, with no per-project process and no assumption that projects are unrelated, so programs (180) are a later addition, not a rewrite.

## Architectural Principles

- **Observe, decide, act.** The Runner has three stages, and only the middle one decides. **Observe** reads external surfaces (child-process exit, `sq runs wait`, `cf status --json`, `cf list slices --json`, CF snapshots, review artifacts, `git status`) and writes what it learned into the store; it never chooses anything. **Decide** is a pure function from store state plus the routing table to the next actions; it does no I/O. **Act** issues each action as a journaled command (`journal_issue` before, result recorded after) and nothing else. Every command with a side effect is a journaled command kind with required keys, an observer, and a re-issue rule. After a crash, an entry recovery marks `not_applied` may be issued again, and one marked `unknown` escalates. In v1 the kinds are `sq_run` and `cf_write`. The Runner makes no git writes, because Squadron's code pipelines enter, commit, and merge slice branches themselves. Reads are observations and are not journaled. Each read is recorded (in the store, or in the decision record that uses it) before Decide runs, so Decide stays pure and every decision can be recomputed from its record.

- **The tick never waits.** The tenant obligation is binding: `tick()` is synchronous and returns promptly. Long work is a subprocess the Runner launches, then observes on later ticks until it finishes. Every subprocess the tick itself waits on (a `cf ... --json` read, `git status`, a one-poll `sq runs wait --timeout 0`) is short and runs under a per-call timeout from settings. A call that times out is a fault for that project, not a stall for the rest. Within one tick, each project goes through a fixed order: apply pending intents, observe and ingest finished work, route ingested outcomes, then decide and act for nodes that were runnable when the tick's observation ran. A successor that becomes runnable by routing is decided on the next tick, after a fresh observation, so no decision uses a stale read. Routing works from store state, not from the tick's flow: an ingested outcome with no decision record is unrouted, and the next tick routes it. A crash between ingestion and routing therefore loses nothing.

- **Faults stay in their project.** An exception while handling one project (a `cf` that returns unexpected JSON, a vanished project directory, a failed command launch) is logged at ERROR with its traceback, recorded against the affected node as a `blocked_on_human` escalation carrying the error (where a fault has no node, such as a failed plan read, slice design decides what it attaches to), and does not stop the tick for other projects. This per-project handler is the Runner's one process-boundary catch, named here so it is not repeated elsewhere. A store that cannot be written is not a project fault: it is a process failure, the process exits, and 100's recovery takes over on restart. Every fault escalates in v1, including transient ones such as a timeout. A retry class for transient faults is added once the first proof shows which faults actually recur.

- **Observe outcomes from the contract, not the conversation.** What a run did is read from Squadron's machine surfaces (`sq runs wait` exit codes, `--output json`, review artifact frontmatter; never the run-state file, which Squadron calls internal) and CF's (`cf status --json`, `projects.json` snapshots), never from stdout prose, `cf next`'s `recommendation` text, or exit code alone (`sq run` exits 0 for both completed and paused).

- **Unknown escalates.** A missing field, an unparseable artifact, an unrecognized run status, a review with no attributable node: each becomes an explicit unknown routed to a human, never a guessed value. Routing rules may match "unknown"; they may not default it away. This is also how upstream drift is handled: a renamed or removed field is a missing field. The Runner does not gate on upstream version numbers; it depends on shapes, and a shape it cannot read escalates. A few shapes it cannot work without at all: `sq run --run-id`, `sq runs wait`, and `cf status --json`. These are probed once at start from the tools themselves. A missing one refuses to start the Runner tenant with an error naming it, rather than failing on the first run.

- **The table is static config.** The routing table and every threshold in it are loaded at start and never mutated at runtime. Each table version's full content is kept in the store the first time a decision uses it, so any decision can be recomputed from its record alone. Editing the table means restarting the resident process, which 100's recovery already makes safe, including for runs in flight. Calibration evidence (100's report, later 140's) produces *recommendations* the PM applies by editing the table. This is also Squadron's permanent metrology constraint.

- **Closed vocabularies for everything routed on.** Command kinds, intent kinds, inferred tiers, route outcomes, and lifecycle steps are enumerations defined once. Squadron's free-form `category` and CF's prose are carried as evidence and never matched as structure.

- **Respect the store's rules as the store's caller.** The Runner writes through 100's public API only, follows the attribution rule and D5 to the letter, never caches `project_ids`, and adds tables only through 100's migration mechanism. Where the Runner needs something the contract lacks, the contract changes first.

## Current State

- **Amoeba (100 complete).** The resident process hosts tenants and reconciles every journaled command before any tenant ticks. The store has the node tree, the six statuses, `block`/`resolve`, the two Runner queries (`runnable`, `blocked`), the command journal (`cf_write`, `sq_run`), verdict and finding records with a computed trust label (`standing`) and round-over-round `finding_changes`, checks with `vacuous ≠ passed`, `record_runner_report`, the `intent` channel (`pending_intents` / `acknowledge_message`), CF snapshots, and the change feed. A stand-in Runner in `tests/contract/` proves the path end to end. Requirements already binding on 120 are written in the contracts: the attribution rule, D5 points 3 and 5, `run_id` in every `sq_run` result, "a resume whose run is missing is a failed command", the tenant obligation, and no secrets in journal entries. Two gaps the Runner will hit: `done` is documented as terminal but not enforced by `update_node_status`, and no inbox kind creates nodes ("node creation from outside the process arrives with 120"). The intent body format is undefined, by design: it is 120's and 160's.

- **Squadron (observed 20261020).** Per-phase pipelines exist for architecture (P2), slice design (P4), tasks (P5), and implementation (P6), plus combined (P45, P56, P456) and plan-wide batch pipelines (`slices-plan`, `tasks-plan`, `implement-plan`). Each phase pipeline revises until its review passes and checkpoints otherwise; a non-interactive checkpoint exits with the run saved as `paused`. There is no slice-plan (P3) pipeline. `sq run` has no JSON output and exits 0 for completed *and* paused. The supported outcome contract is `sq runs wait <id>`: one exit code per outcome (completed, failed, paused, timed out, not found, unreadable, unknown status, orphaned). The run-state file holds more (checkpoint reason, step, verdict) but is internal and may change (sq-cf, 20261020). A public `--run-id` lets a caller choose the run id (on main since 20261020, next patch release). Findings now carry `location_verified`; `verdictSource` (`stated | derived | imposed`) is in frontmatter and JSON; `stop_reason` and related fields are JSON-only. Still absent: a tier field (S1), a review-completed event (S8), escalation on checkpoint (SQ 185). Runs can fail with `cost_cap` under `pipeline.max_cost_usd`.

- **Context Forge (observed 20261020).** `cf status --json` exposes `activeSlice.status` including `pending-review`, `review-failed`, and the new `pending-decision` (with `pendingDecisions[]`), plus `gateInfo`. `cf set` has no JSON output; writes are confirmed by reading back. Live pointers are per worktree. There is no execute mode; CF stays advisory and Amoeba is the executor. The two silent-ungate hatches (`review: none`, `dateCreated` before the effective date) still exist.

**Constraints this imposes:** the Runner observes run outcomes by polling `sq runs wait` rather than from events; the pause reason is not machine-readable until S10; and phases with no Squadron pipeline (P3, P7, merges, host cutovers) have no automated executor, so they are human steps for now.

## Envisioned State

At completion, the Runner is one tenant, ticking last in the resident process, that drives every project in the supervisor directory.

**The lifecycle model.** For each project, the Runner keeps 100's node tree in step with CF: initiatives and slices as CF reports them (`cf list slices --json`, `cf status --json`; the Runner parses no plan markdown of its own), and below each slice a node per lifecycle step (design, tasks, implementation) with a gate node where CF or the routing table requires a review. The Runner is the only creator of nodes; the PM (and later the Translator) steers through `intent` messages (what to drive, how far, and when to stop) and never writes nodes directly. Every lifecycle step maps to exactly one of: a Squadron pipeline the Runner may run, a CF write it may make, or a **human step** that is a `blocked_on_human` node from the moment it becomes current.

**Who is authoritative for what.** CF owns the plan and the pointers: which slices exist, their order, and which slice and phase are active. The store owns everything CF does not hold: evidence, routing decisions, blocked-states, and attempt counts. The two meet only through reconciliation, which runs whenever a `cf_project_changed` entry arrives. A node's identity is 100's opaque store id. Its link to CF is the slice's index within its project, held in the node's CF reference; the slice's name and file name are display data and never used to match. Reconciliation follows four rules:
- A slice CF reports and the tree lacks gets nodes.
- A renamed slice keeps its node.
- A node whose index CF no longer reports is never deleted; it escalates as orphaned. A renumbered slice is therefore one orphan plus one new node, and the PM sorts out which is which.
- CF's pointers are not commands. The Runner drives what intents tell it to, and sets CF's pointers itself (a journaled `cf_write`) before it dispatches a node. A pointer someone else moves changes nothing, unless it moves away from a node with a run in flight, in which case that node escalates.

**The loop, per tick, per project.** Apply pending intents. Observe in-flight runs and ingest the outcome of each that finished. Route each ingested outcome. Decide the next action for every node now runnable, and issue it, journaled.

**Outcome ingestion.** A finished run yields evidence, not a verdict to trust: the run's final status and checkpoint, every review artifact it wrote (recorded from the artifact through 100's parser, attached by the attribution rule, marked `runner_issued` in the same transaction that resolves the journal entry), CF's gate state for the slice, and any checks the Runner ran itself. A run that exited paused becomes a `blocked_on_sq_checkpoint` node holding its run id; a run that failed, timed out, hit its cost cap, or cannot be found becomes a `blocked_on_human` node with the reason.

**The routing engine.** Each outcome is reduced to routing inputs: verdict and its `standing`, each finding's inferred tier, `finding_changes` against the last round, gate state, check outcomes, and run status. The table maps these to exactly one route from a closed set: **advance** (mark done, make the next node runnable), **rerun** (a fresh run of the same step, for a run that *completed* with an outcome the table does not accept, such as CONCERNS on a step that requires PASS; bounded by an attempt limit counted per node and step), or **escalate** (block on a human). A rerun relaunches the same phase pipeline. Squadron's phase pipelines run with `existing: keep`, so a rerun re-reviews and revises the work already on disk instead of regenerating it, and its revise loop takes the fresh review as feedback. Squadron accepts instructions only when resuming a batch item (`--resume <id> --item N --instructions`). For per-phase runs, a resolution's instructions therefore have no path into Squadron, and a resolution that depends on them leaves the next step to a human. A rerun is never used for a paused run, which is always resumed, never restarted. Every application writes a decision record (inputs, rule id, table version, Amoeba's version, route), which is both the audit trail and the raw material for "build by inducing failure." There is no judge route in v1. Instead, the table marks escalations the Judge would be asked about as judge-eligible, a field on the escalate decision. That gives 140 its first evidence (which escalations it would have taken) before it exists. 140 adds the **judge** route, and the eligible rules switch to it, starting at the concept's always-escalate threshold.

**Tier inference, after the first proof.** The concept locks tier inference inside Amoeba for v1, and it stays in scope, but it is not the first routing the Runner does. The first routing table matches only what is already recorded (run status, verdict, `standing`, recurrence, gate state, ungate hatches) and escalates everything else. The first proof's wrong stops then show which findings need a tier. Inference uses closed signals only: severity, `location_verified`, `standing`, recurrence, and the Runner's own Tier-1 predicates. A finding the rules cannot classify is Tier 2, never Tier 1. When Squadron emits a tier (S1), it becomes one more input and the inference rules shrink.

**Resolution and resumption.** A human resolution or (later) a Judge result lands through the inbox and flips the node to runnable. The Runner's next action for a resolved checkpoint node is an explicit `sq run --resume <run_id>` carrying the resolution's decision; for a resolved escalation, whatever the resolution says (accept and advance, rerun with instructions, or stop the node). A resume whose run is missing is a failed command: the node blocks on a human, and the run is never relaunched.

**What it emits.** Nothing new on the wire: every node, verdict, and message write already appears on 100's feed. A subscriber (the notification bridge, a status view) sees the Runner's work as node status changes and escalation messages.

## Technical Considerations

- **Dispatch granularity — per-phase by default, batch where it fits (PM, 20261020).** Squadron offers per-phase pipelines (P4, P5, P6), combined ones (P456), and plan-wide batch runs (`slices-plan`, `tasks-plan`, `implement-plan`). The default is **one phase of one slice per run**, so every gate CF or the routing table cares about falls between runs, where the Runner acts. Batch dispatch is planned for after the first proof, because designing a whole plan's slices in one run (`slices-plan`) will be common. When it lands, the Runner treats a batch run as one dispatch whose per-item outcomes (Squadron's batch report, `items[]`) map back onto per-slice nodes, and it acts only at the items Squadron flags or pauses on. Resuming one flagged item is an explicit per-item resume with the resolution's decision. Which lifecycle steps may be dispatched as a batch, and the mapping from report items to nodes, are slice design's.

- **Escalations from inside a run are the Runner's main input.** Within a run, Squadron's agents decide and revise on their own; what reaches the Runner is the residue: a checkpoint because a loop did not converge, a flagged batch item, a task the agent marked blocked for a person, a decision CF marks pending. These are the points where the agent was unsure of an outcome or a decision. Before 140, every such point routes to a human, carrying what the agent reported. After 140, the routing table can send the evaluable ones to the Judge first and escalate only what it cannot resolve with consensus. The route is the same table edit either way; nothing in the Runner changes when 140 arrives.

- **Run identity (dependency S9, delivered 20261020).** Squadron now has a public `sq run ... --run-id <id>` (on main as ca9608b0, not yet released), with a fixed id rule (letters, digits, `.`, `_`, `-`; first character a letter or digit; at most 128). An existing id is refused before anything runs, and every fresh run prints `run_id=<id>` on stderr before its first step. The Runner mints each run's id, journals it, and passes it with `--run-id`, which makes recovery exact: an entry's run is found by id, not matched. It also lets the Runner mint the verdict id at journal time (100's retry rule). Because a taken id is refused, a crash between journaling and launch can never produce a second run under the same entry. 100's matching recovery stays only for entries journaled without an id, which means runs from before this change. Note that 100's recovery observer and paused-run pruning both read Squadron's run-state files, which sq-cf calls internal; they move to `sq runs wait` (and S10, once it exists) as part of this work.

- **Observing a run without blocking the tick.** Runs are launched **detached**: in their own session, with stdin from `/dev/null` (100's non-TTY invariant: no implicit resume), and stdout and stderr redirected to per-run log files under the supervisor directory. So a run is never tied to the resident process's pipes or lifetime, and it survives a stop or a crash of the resident process. Observation is by run id, never by process handle: each tick, the Runner calls `sq runs wait <id> --timeout 0` for each in-flight run. That call reads the run's state once and never sleeps (a pinned Squadron contract since 20261020): exit 4 means still running, and any other code is the outcome. The same call serves runs launched in this lifetime and runs adopted by recovery after a restart, so there are no long-lived wait processes to manage. Liveness is Squadron's to report: a run whose process is gone comes back as `orphaned`, which escalates. A run that never ends hits a per-pipeline time bound in the table, after which the node escalates; the Runner does not kill runs on its own. `sq runs wait` reports *that* a run paused, not why; routing on the pause reason (step, verdict) needs a machine-readable `sq runs wait --json` or `sq runs show --json` from Squadron (dependency S10). Until then the reason comes from the review artifacts the run wrote, and an unexplained pause escalates.

- **Concurrency is bounded by the working tree.** Two runs that write files in one checkout collide, so a checkout runs one pipeline at a time, and every v1 pipeline counts, since all of them write and commit. The rule is a runnability filter in Decide, keyed on the checkout path CF reports for the node's worktree. A checkout is held from launch until its run is no longer running or paused, because a paused run still has its slice branch checked out. Other slices in that checkout wait until it is released. Parallel slice work means separate CF worktrees, which is already the PM's practice. Squadron's `max_cost_usd` bounds the spend of each run; a `cost_cap` failure escalates and is never retried automatically. A global limit on in-flight runs across projects waits until real multi-project use shows it is needed.

- **Squadron does the git work; the Runner checks before it dispatches.** Squadron's pipelines commit their own output (`commit_each_iteration`), and its code pipelines enter the slice branch and merge it back into its target, with a merge commit, no push, and a clean abort on conflict. So a successful run leaves a committed tree, and the Runner itself writes nothing to git. The PM works in the same checkouts, so before dispatching any run the Runner observes the tree, and dispatches only if it is clean and on the target or on this node's slice branch. Otherwise the node escalates. The Runner never stashes, resets, or forces anything.

- **Merge policy is a choice of pipeline.** **Merging is a human step by default** ("no merge before code review", merge only on the PM's word). It is a per-project policy, not a fixed rule: for simpler apps and projects the PM can let Amoeba merge a slice into its target after its code review passes (PM, 20261020). The policy lives in static config, defaults to human, and is recorded on each dispatch decision.
  - **Auto-merge:** the Runner dispatches Squadron's P6, which merges.
  - **Human merge:** Squadron has no switch to skip P6's merge step. Amoeba therefore ships its own pipeline: P6 without the merge, run under a different name, through Squadron's support for project-local pipelines. The node then waits on a human merge step, and the Runner observes the merge in git (Squadron's own rule: git, not CF's checkboxes, says a slice is merged).
  - The variant is temporary and will drift from P6. It goes away when Squadron adds a `merge` param (dependency S11).
  - Never, under any policy: the Runner merges, deletes branches, or pushes on its own; and nothing merges to `main` when an integration branch is set.

- **Gates come from CF's structured status, and are not trusted alone.** The Runner reads `activeSlice.status` and `gateInfo` through `cf status --json`, never `cf next`'s prose. `pending-decision` is a human step. A CF gate that clears on a `derived` or `imposed` verdict, or on a review whose `standing` is not trustworthy, is still routed on the store's view, not CF's. The two silent-ungate hatches are Tier-1 checks the Runner runs: if either is present, the node escalates; the Runner never writes `review: none`.

- **What the routing table matches on.** Inputs are closed: run status, verdict, standing, inferred tier, finding severity, recurrence (`new` / `recurring` / `gone`), check standing, attempt count, node kind, and lifecycle step. Rules are ordered, first match wins, and the table must end in a catch-all that escalates. The table format, and where it lives (per supervisor, with per-project overrides or not), are slice design's.

- **Tier-1 predicates are cheap and must be honest.** Field data shows validators that exit 0 having checked nothing and `main` carrying known failures. Every check the Runner runs records what it examined, using 100's check records; a vacuous check is never a pass. The first checks are the ones the first proof needs (ungate hatches, "the validator examined more than zero files"). Baseline-diffed test checks come after the first proof, when its stops show they are needed.

- **Intent is a closed, declarative command set.** Before the Translator exists, the PM steers the Runner by submitting intents directly. The vocabulary is small and structural, and every intent sets a desired state on one target node: driven or not, the lifecycle step to drive up to, held or not. "Pause" and "resume" are therefore held true and held false, not events. Applying an intent twice is the same as applying it once. Targets form the node tree (project, initiative, slice), and what governs a node is the nearest intent on its path: the node's own, else its slice's, and so on up the tree. A narrow intent overrides a broad one for its subtree regardless of arrival order, with one exception: held true on any ancestor holds the whole subtree, so a broad stop always works. For one target, the later intent in the store's message order replaces the earlier. Applying an intent and acknowledging it happen in one store transaction (the Runner is in-process and the sole writer), so a crash replays nothing. An intent that is already satisfied (drive to a step the node has passed) is acknowledged as a no-op. One the Runner cannot apply is acknowledged with an explicit rejection rather than ignored. This vocabulary is the contract 160 will translate natural language into; 160's command-authority whitelist (OQ5) is a subset of it.

- **Contract changes the Runner needs from 100.** Enforce `done` as terminal in `update_node_status`; register the Runner's review-producing `sq_run` use in `REVIEW_PRODUCING_KINDS`, add the minted run id to `sq_run`'s required keys, and make its observer find the run by that id, with enum member, keys, and observer kept together as the process contract requires; give an intent's acknowledgment an outcome (applied, no-op, rejected with a reason) that the submitter can read; move 100's recovery observer and paused-run pruning off Squadron's internal run-state files onto its supported surfaces (`sq runs wait` now, S10 when it lands); add the routing-decision, table-version, and attempt-count tables through the migration mechanism. Node creation from outside the process stays out: the Runner is the only creator of nodes, and outside parts steer it with intents.

- **Do not foreclose programs.** Cross-project dependency edges (180) will make a node in one project wait on a node in another. The decision step therefore reads "is this node's predecessor done?" through one function, so a cross-project predecessor is an added input, not a rewrite.

## Anticipated Slices

Exploratory, not a commitment:

Up to the first proof:

- **Runner tenant and control surface.** The tenant composed after `standard_tenants`; observe / decide / act; detached launch and observation by run id; per-project fault isolation; run identity; the 100 contract changes above. Proof: a no-op lifecycle step journaled, run, observed, and recovered across a `kill -9` of the resident process.
- **Lifecycle model and intent.** Projecting CF's slices and pointers into the node tree and reconciling it on `cf_project_changed`; the step map (pipeline, CF write, or human step) for each node kind; the intent vocabulary with idempotent apply and acknowledgment outcomes.
- **Run dispatch and outcome ingestion.** Per-phase pipeline dispatch; ingesting reviews under the attribution rule and D5; paused, failed, timed-out, cost-capped, orphaned, and missing runs as blocked-states; explicit resume with the resolution's decision.
- **Routing engine.** The table as static config with stored versions; decision records; advance / rerun / escalate with attempt limits; judge-eligible marks on escalations, for 140. Routes on recorded evidence only, with no tier inference yet.
- **Gates, git, and human steps.** CF review and decision gates, ungate-hatch checks, the clean-tree dispatch precondition, the per-project merge policy (human by default, with Amoeba's P6-without-merge pipeline), and other human steps.
- **First proof.** One project, one PM-chosen unstarted unit, driven end to end. Its wrong stops become the next routing rules.

After the first proof:

- **Batch dispatch** (planned, PM 20261020). `slices-plan` first, with per-item outcomes mapped to slice nodes.
- **Tier inference and baseline-diffed checks**, shaped by the first proof's stops.
- **Multi-project scheduling.** Fairness across projects and a global in-flight run limit, once real multi-project use calls for them.
