# Architecture: Runner & Routing Engine

## Overview

The Runner is the project's core artifact: a deterministic state machine that drives a project through its Context Forge (CF) / Squadron (SQ) lifecycle with zero discretion of its own. Its loop is the concept's: *while runnable work exists, issue a command, read what comes back, apply the routing table, and advance, send to the Judge, or write a blocked-state.* The routing engine is the table and the rule-application step inside that loop. Together they are the only part of Amoeba that **acts**: the substrate (100) stores and observes, the Judge (140) evaluates, the Translator (160) interprets, and the Runner is what turns state into the next command.

**The problem it addresses.** With 100 complete, Amoeba can remember everything and notice everything, and do nothing. A slice still advances only when a human runs `cf set`, launches `sq run`, reads the review, decides whether CONCERNS is acceptable, resumes a paused run, and does it again. Most of those decisions are mechanical. Squadron has since automated the *within-artifact* half (revise → review → gate loops inside one pipeline run) but stops at the run boundary: a run that cannot converge exits paused, and nothing picks it up, carries it across days, or decides what the next run should be.

**Scope.** This component owns: (1) the **Runner tenant**, hosted in the resident process beside the shipped tenants; (2) the **control surface**, the closed set of CF and SQ commands the Runner issues, each journaled before it runs and observed until it finishes; (3) the **lifecycle model**: how a project's CF plan and pointers become nodes in 100's tree, and what "runnable" means for each node kind; (4) **outcome ingestion**: turning a finished run's reviews, run state, and CF gate state into store records under 100's evidence rules; (5) the **routing engine**: tier inference, the routing table, and a recorded decision for every outcome; (6) the **intent vocabulary**: what an `intent` message may ask the Runner to do. It does **not** own consensus or judge invocation (140), natural-language interpretation or notification (160), within-artifact revise loops (Squadron's), or the store, inbox, feed, and observers it builds on (100).

**Motivation.** Everything before this initiative is plumbing for it, and everything after it (140, 160, 180) attaches to its decisions. It is also where the project's method lives: "build by inducing failure" edits the routing table, so the table has to be data, auditable, and the only place routing behavior is defined.

## Design Goals

- **Zero discretion, total auditability.** Every action the Runner takes is the output of a fixed rule over recorded inputs. Given the store's contents and the routing table version, any decision can be recomputed and explained after the fact: which rule fired, on which evidence.

- **Unattended between decisions that need a person.** A slice goes from "design pending" to "implemented and reviewed" without a human touching it, *unless* the routing table says a human is the next step. When it does, the Runner writes the blocked-state, moves on to other runnable work, and resumes the node when the resolution lands, hours or days later, across restarts.

- **Squadron does the work; the Runner decides what work is next.** The Runner never reimplements what a Squadron pipeline already does (generation, review, revise loops, gating inside a run). It chooses which pipeline runs on which node, and routes what the run returns.

- **One edit point for routing.** Changing which route a kind of outcome takes means editing the routing table and nothing else. Code defines a closed set of named inputs and predicates (what a "recurring finding" or a "vacuous check" is); the table alone decides what each combination of them does. No route is chosen in a code branch outside the table.

- **Many projects, one loop.** The Runner serves every project in the supervisor directory from one tenant, with no per-project process and no assumption that projects are unrelated, so programs (180) are a later addition, not a rewrite.

## Architectural Principles

- **Observe, decide, act.** The Runner has three stages, and only the middle one decides. **Observe** reads external surfaces (child-process exit, `sq runs wait`, `cf status --json`, `cf list slices --json`, CF snapshots, review artifacts, `git status`) and writes what it learned into the store; it never chooses anything. **Decide** is a pure function from store state plus the routing table to the next actions; it does no I/O. **Act** issues each action as a journaled command (`journal_issue` before, result recorded after) and nothing else. An action that is only a store write, such as blocking a current human step, is applied in one transaction and is not journaled, because it has no external side effect to recover (slice 123, D9). Every command with a side effect is a journaled command kind with required keys, an observer, and a re-issue rule. After a crash, an entry recovery marks `not_applied` may be issued again, and one marked `unknown` escalates. In v1 the kinds are `sq_run` and `cf_write`. The Runner makes no git writes, because Squadron's code pipelines enter, commit, and merge slice branches themselves. Reads are observations and are not journaled. A read is written to the store only when it changes something (a run's outcome is ingested, a check's result differs from the last one recorded) or when a decision uses it, in which case it goes into that decision's record. A poll that finds nothing new writes nothing. Decide sees only these recorded values, so it stays pure, and every decision can be recomputed from its record.

- **The tick never waits.** The tenant obligation is binding: `tick()` is synchronous and returns promptly. Long work is a subprocess the Runner launches, then observes on later ticks until it finishes. Every subprocess the tick itself waits on (a `cf ... --json` read, `git status`, a one-poll `sq runs wait --timeout 0`) is short and runs under a per-call timeout from settings. A call that times out is a fault for that project, not a stall for the rest. The tick as a whole also has a deadline, checked before every subprocess call, not just between projects. Work the tick does not reach goes first on the next tick. A project cut off partway through Observe starts its observation again from the top, which is safe because observation only reads. Worst-case tick length is therefore the deadline plus one per-call timeout. Observe reads a fixed set of things for each project that an intent says to drive or that has a run in flight: its CF status, its initiatives and slices, the state of each checkout its nodes use, and the state of each in-flight run. Initiatives and slices are the exception: they are read for every linked project on a plan read interval, because intents need their nodes to exist before anything is driven (slice 123, D7). Decide never needs to request a read of its own. Within one tick, each project goes through a fixed order: apply pending intents, observe and ingest finished work, route ingested outcomes, then decide and act for nodes that were runnable when the tick's observation ran. A successor that becomes runnable by routing is decided on the next tick, after a fresh observation, so no decision uses a stale read. Routing works from store state, not from the tick's flow: an ingested outcome with no decision record is unrouted, and the next tick routes it. A crash between ingestion and routing therefore loses nothing.

- **Faults stay in their project.** An exception while handling one project (a `cf` that returns unexpected JSON, a vanished project directory, a failed command launch) is logged at ERROR with its traceback, recorded against the affected node as a `blocked_on_human` escalation carrying the error (a fault with no node, such as a failed plan read, raises a project-scoped escalation instead; see the contract changes below), and does not stop the tick for other projects. This per-project handler is the Runner's one process-boundary catch, named here so it is not repeated elsewhere. A store that cannot be written is not a project fault: it is a process failure, the process exits, and 100's recovery takes over on restart. Every fault escalates in v1, including transient ones such as a timeout. A retry class for transient faults is added once the first proof shows which faults actually recur. Escalations cannot storm: the store allows one open blocked state per node, so a fault that recurs every tick on a blocked node adds nothing. A fault on a node whose run is in flight is logged, the run keeps being observed and ingested, and the node blocks when the run ends. A fault with no node reaches the PM through its project-scoped escalation, with at most one open per project and fault kind.

- **Observe outcomes from the contract, not the conversation.** What a run did is read from Squadron's machine surfaces (`sq runs wait` exit codes, `--output json`, review artifact frontmatter; never the run-state file, which Squadron calls internal) and CF's (`cf status --json`, `projects.json` snapshots), never from stdout prose, `cf next`'s `recommendation` text, or exit code alone (`sq run` exits 0 for both completed and paused).

- **Unknown escalates.** A missing field, an unparseable artifact, an unrecognized run status, a review with no attributable node: each becomes an explicit unknown routed to a human, never a guessed value. Routing rules may match "unknown"; they may not default it away. This is also how upstream drift is handled: a renamed or removed field is a missing field. The Runner does not gate on upstream version numbers; it depends on shapes, and a shape it cannot read escalates. A few shapes it cannot work without at all: `sq run --run-id`, `--decision` on a plain `sq run --resume`, `sq runs wait --json`, `cf status --json`, `cf list initiatives --json`, and `cf list slices --json`. The read-only ones are probed once at start, by running them:
- `sq runs wait <fresh unused id> --timeout 0 --json` must return the not-found outcome document.
- `cf status --json` and `cf list initiatives --json` must parse for a linked project. `cf list slices --json` is not probed. Without an index it reads a project-level pointer that is empty on worktree-scoped projects, so its shape is checked on each plan read instead (slice 123, D11).

A failed `sq` probe refuses to start the resident process, with an error naming the shape. A `cf` probe runs once per CF link, because it needs a CF project id, and a failure escalates for that link's project only (slice 122, D9). The two flags can't be probed without a real run, so they are checked on first use instead.
- **Launch:** Squadron exits 2 on a usage error before anything runs, so an exit 2 from a launch stops the resident process with an error naming the command, because a process running on with its Runner stopped would be a silent fallback (slice 122, D6).
- **Resume:** exit 2 also means "accept needs a run paused at a loop step", so an exit 2 from a resume is a failed command that escalates its node with Squadron's message attached.

No probe reads help text.

- **The table is static config.** The routing table and every threshold in it are loaded at start and never mutated at runtime. Each table version's full content is kept in the store the first time a decision uses it, so any decision can be recomputed from its record alone. Editing the table means restarting the resident process, which 100's recovery already makes safe, including for runs in flight. Calibration evidence (100's report, later 140's) produces *recommendations* the PM applies by editing the table. This is also Squadron's permanent metrology constraint.

- **Closed vocabularies for everything routed on.** Command kinds, intent kinds, inferred tiers, route outcomes, and lifecycle steps are enumerations defined once. Squadron's free-form `category` and CF's prose are carried as evidence and never matched as structure.

- **Respect the store's rules as the store's caller.** The Runner writes through 100's public API only, follows the attribution rule and D5 to the letter, never caches `project_ids`, and adds tables only through 100's migration mechanism. Where the Runner needs something the contract lacks, the contract changes first.

## Current State

- **Amoeba (100 complete).** The resident process hosts tenants and reconciles every journaled command before any tenant ticks. The store has the node tree, the six statuses, `block`/`resolve`, the two Runner queries (`runnable`, `blocked`), the command journal (`cf_write`, `sq_run`), verdict and finding records with a computed trust label (`standing`) and round-over-round `finding_changes`, checks with `vacuous ≠ passed`, `record_runner_report`, the `intent` channel (`pending_intents` / `acknowledge_message`), CF snapshots, and the change feed. A stand-in Runner in `tests/contract/` proves the path end to end. Requirements already binding on 120 are written in the contracts: the attribution rule, D5 points 3 and 5, `run_id` in every `sq_run` result, "a resume whose run is missing is a failed command", the tenant obligation, and no secrets in journal entries. Two gaps the Runner will hit: `done` is documented as terminal but not enforced by `update_node_status`, and no inbox kind creates nodes ("node creation from outside the process arrives with 120"). The intent body format is undefined, by design: it is 120's and 160's.

- **Squadron (observed 20261020).** Per-phase pipelines exist for architecture (P2), slice design (P4), tasks (P5), and implementation (P6), plus combined (P45, P56, P456) and plan-wide batch pipelines (`slices-plan`, `tasks-plan`, `implement-plan`). Each phase pipeline revises until its review passes and checkpoints otherwise; a non-interactive checkpoint exits with the run saved as `paused`. There is no slice-plan (P3) pipeline. `sq run` has no JSON output and exits 0 for completed *and* paused. The supported outcome contract is `sq runs wait <id>`: one exit code per outcome (completed, failed, paused, timed out, not found, unreadable, unknown status, orphaned). The run-state file holds more (checkpoint reason, step, verdict) but is internal and may change (sq-cf, 20261020). A public `--run-id` lets a caller choose the run id. Code pipelines take `-p merge=false`, and a plain resume takes `--decision accept|retry` and `--instructions`. All three were released in squadron-ai 0.23.5 on 20261020. Findings now carry `location_verified`; `verdictSource` (`stated | derived | imposed`) is in frontmatter and JSON; `stop_reason` and related fields are JSON-only. Still absent: a tier field (S1), a review-completed event (S8), escalation on checkpoint (SQ 185). Runs can fail with `cost_cap` under `pipeline.max_cost_usd`.

- **Context Forge (observed 20261020).** `cf status --json` exposes `activeSlice.status` including `pending-review`, `review-failed`, and the new `pending-decision` (with `pendingDecisions[]`), plus `gateInfo`. `cf set` has no JSON output; writes are confirmed by reading back. Live pointers are per worktree. There is no execute mode; CF stays advisory and Amoeba is the executor. The two silent-ungate hatches (`review: none`, `dateCreated` before the effective date) still exist.

**Constraints this imposes:** the Runner observes run outcomes by polling `sq runs wait` rather than from events; the Squadron surfaces it relies on (S9 through S13) were released in squadron-ai 0.23.5 on 20261020; and phases with no Squadron pipeline (P3, P7, merges, host cutovers) have no automated executor, so they are human steps for now.

## Envisioned State

At completion, the Runner is one tenant, ticking last in the resident process, that drives every project in the supervisor directory.

**The lifecycle model.** For each project, the Runner keeps 100's node tree in step with CF: initiatives and slices as CF reports them (`cf list initiatives --json` for initiative nodes, `cf list slices --json` for each initiative's slices, `cf status --json` for pointers and gates; the Runner parses no plan documents of its own; reading a document's YAML frontmatter, as the ungate-hatch checks do, is an observation, not plan parsing), and below each slice a node per lifecycle step (design, tasks, implementation, merge). v1 has no gate nodes: each phase pipeline reviews inside its run, and CF's gate is a dispatch check and routing input (slice 123, D3). The Runner is the only creator of nodes; the PM (and later the Translator) steers through `intent` messages (what to drive, how far, and when to stop) and never writes nodes directly. Every lifecycle step maps to exactly one of: a Squadron pipeline the Runner may run, a CF write it may make, or a **human step** that is a `blocked_on_human` node from the moment it becomes current. In v1 no step is a CF write: the pointer write is part of dispatching a pipeline step (slice 123, D3). The v1 step map:

| Lifecycle step | Node level | v1 executor |
| --- | --- | --- |
| Architecture (P2) | initiative | Human step. P0–P2 are PM-approved phases; Squadron's P2 pipeline is not dispatched in v1. |
| Slice plan (P3) | initiative | Human step. Squadron has no slice-plan pipeline. |
| Slice design (P4) | slice | Squadron `P4` |
| Tasks (P5) | slice | Squadron `P5` |
| Implementation and code review (P6) | slice | Squadron `P6`, with `merge=false` unless the project's merge policy is auto |
| Merge | slice | Human step, or inside `P6` under auto-merge |
| Phase 7, and host cutovers | initiative | Human step (P7 is PM-approved) |


**Who is authoritative for what.** CF owns the plan and the pointers: which slices exist, their order, and which slice and phase are active. The store owns everything CF does not hold: evidence, routing decisions, blocked-states, and attempt counts. The two meet only through reconciliation. It runs whenever the initiative or slice list Observe reads differs from the tree: editing a plan document does not touch `projects.json`, so the feed alone would miss a new slice. It also runs on each `cf_project_changed` entry for a successful snapshot that changed a pointer. A failed snapshot (`changed` null) or a recovery with nothing changed (`changed: []`) triggers nothing. A node's identity is 100's opaque store id. Its link to CF is the slice's index within its project, held in the node's CF reference; the slice's name and file name are display data and never used to match. Reconciliation follows four rules:
- A slice CF reports and the tree lacks gets nodes.
- A renamed slice keeps its node.
- A node whose index CF no longer reports is never deleted; it escalates as orphaned, unless it is already done (no person is needed) or already blocked (its open escalation stands) (slice 123, D5). A renumbered slice is therefore one orphan plus one new node. The orphan keeps its history (verdicts, attempts, recurrence) and the new node starts fresh, so renumbering a slice resets its round-over-round comparison and attempt count. That loss is accepted in v1; a relink intent is the fix if renumbering turns out to be common.
- CF's pointers are not commands. The Runner drives what intents tell it to, and sets CF's pointers itself (a journaled `cf_write`) before it dispatches a node. Dispatch is therefore two actions on two ticks: the pointer write, and then, once its read-back is recorded, the run. CF routes a write to a worktree by the caller's working directory, so the write and its read-back run in the checkout of the worktree whose index range holds the slice, and the read-back checks the slice index, path and worktree (slice 125, D1, D2). A pointer someone else moves changes nothing, unless it moves away from a node with a run in flight. In that case a project-scoped escalation names the node while the move lasts, because a node with a run in flight blocks only when its run ends. Only snapshots recorded after the Runner's own pointer write are read, so its own writes never count as a move (slice 125, D11).

**The loop, per tick, per project.** Apply pending intents. Observe in-flight runs and ingest the outcome of each that finished. Route each ingested outcome. Decide the next action for every node now runnable, and issue it, journaled.

**Outcome ingestion.** A finished run yields evidence, not a verdict to trust: the run's final status and checkpoint, the review behind the run's final verdict (recorded from the artifact through 100's parser, attached by the attribution rule, marked `runner_issued` in the same transaction that resolves the journal entry). Which file that is comes from the outcome document's `reviews` list (S13). That list covers every outcome with a run state and is in write order, so the review behind the final verdict is its last entry. A split review names its part files, and the Runner records all of them. The run is journaled on the step node, and its verdicts attach to the slice node by the attribution rule, linked to the run by its run id (slice 125, D7). A run whose list is empty has no review to record. A listed file that is missing or unparseable is unknown and escalates. Rounds inside one run are Squadron's to compare (its revise loop), and the store's `finding_changes` compares run to run. Alongside the review, ingestion also records CF's gate state for the slice, and any checks the Runner ran itself. A run that exited paused becomes a `blocked_on_sq_checkpoint` node holding its run id; a run that failed, timed out, hit its cost cap, or cannot be found becomes a `blocked_on_human` node with the reason.

**The routing engine.** Each outcome is reduced to routing inputs: verdict and its `standing`, `finding_changes` against the last round (after the first proof, also each finding's inferred tier), gate state, check outcomes, run status, and the run's checkpoint or failure kind. The table maps these to exactly one route from a closed set: **advance** (mark done, make the next node runnable), **rerun** (a fresh run of the same step, for a run that *completed* with an outcome the table does not accept, such as CONCERNS on a step that requires PASS; bounded by an attempt limit counted per node and step), or **escalate** (block on a human). A rerun relaunches the same phase pipeline. Squadron's phase pipelines run with `existing: keep`, so a rerun re-reviews and revises the work already on disk instead of regenerating it, and its revise loop takes the fresh review as feedback. A fresh rerun carries no instructions, because Squadron takes them only on a resume (`--instructions`, which prepends its text to every dispatch of the resumed run). A rerun is never used for a paused run, which is always resumed, never restarted. Every application writes a decision record (inputs, rule id, table version, Amoeba's version, route), which is both the audit trail and the raw material for "build by inducing failure." There is no judge route in v1. Instead, the table marks escalations the Judge would be asked about as judge-eligible, a field on the escalate decision. That gives 140 its first evidence (which escalations it would have taken) before it exists. 140 adds the **judge** route, and the eligible rules switch to it, starting at the concept's always-escalate threshold.

**Tier inference, after the first proof.** The concept locks tier inference inside Amoeba for v1, and it stays in scope, but it is not the first routing the Runner does. The first routing table matches only what is already recorded (run status, verdict, `standing`, recurrence, gate state, ungate hatches) and escalates everything else. The first proof's wrong stops then show which findings need a tier. This changes the order of work inside initiative 120, not its scope: tier inference ships in 120, after the first proof. The trigger is a first-proof stop that recorded evidence alone cannot route. Inference uses closed signals only: severity, `location_verified`, `standing`, recurrence, and the Runner's own Tier-1 predicates. A finding the rules cannot classify is Tier 2, never Tier 1. When Squadron emits a tier (S1), it becomes one more input and the inference rules shrink.

**Resolution and resumption.** A human resolution or (later) a Judge result lands through the inbox and flips the node to runnable. Resolutions form a closed set, limited to what the Runner can actually execute. Anything else is rejected explicitly.
- **A paused run** (`blocked_on_sq_checkpoint`):
  - **retry:** the Runner issues `sq run --resume <run_id> --decision retry`. For an exhausted loop, that reruns the final round once, a paid review round, and either continues or pauses again (pinned, Squadron ce0ddf55).
  - **accept:** the Runner issues `--decision accept`. The paused loop's last review is taken as good enough and the run continues, with no round run. This applies only to the loop the run paused at; a later loop in the same run must still pass on its own. A run paused somewhere other than a loop step refuses this ("needs a run paused at a loop step"). The Runner offers accept only when the run's outcome document says the pause is at a loop (`is_loop` true, S10), so this refusal should not happen; if it does, it is a failed command and escalates.
  - **handled:** the PM dealt with the run themselves (an interactive resume, or work by hand). The Runner re-observes the run and routes whatever it finds.
  - **stop:** the node stops being driven.

  Retry and accept can both carry the resolution's instructions (`--instructions`). The Runner passes them through as data and never writes any itself. (Decisions and instructions on a plain resume are S12: released in squadron-ai 0.23.5 on 20261020.)
- **An escalated completed outcome:**
  - **accept:** advance. The acceptance is recorded in the store, which is what the Runner routes on. It does not change CF's gate: CF computes that from review frontmatter, and nothing in Amoeba edits frontmatter to clear a gate (the guide's hard rule). The store and CF may then disagree about the slice. The disagreement is recorded on the node and shown to the PM rather than reconciled away. If a later Squadron pipeline refuses to run because CF's gate is still failed, that node escalates; clearing CF's gate (a new passing review, or the PM's own CF action) is the PM's call.
  - **rerun:** a fresh run of the step.
  - **stop.** A resume whose run is missing is a failed command: the node blocks on a human, and the run is never relaunched.

**What it emits.** Nothing new on the wire: every node, verdict, and message write already appears on 100's feed. A subscriber (the notification bridge, a status view) sees the Runner's work as node status changes and escalation messages.

## Technical Considerations

- **Dispatch granularity — per-phase by default, batch where it fits (PM, 20261020).** Squadron offers per-phase pipelines (P4, P5, P6), combined ones (P456), and plan-wide batch runs (`slices-plan`, `tasks-plan`, `implement-plan`). The default is **one phase of one slice per run**, so every gate CF or the routing table cares about falls between runs, where the Runner acts. Batch dispatch is planned for after the first proof, because designing a whole plan's slices in one run (`slices-plan`) will be common. When it lands, the Runner treats a batch run as one dispatch whose per-item outcomes (Squadron's batch report, `items[]`) map back onto per-slice nodes, and it acts only at the items Squadron flags or pauses on. Resuming one flagged item is an explicit per-item resume with the resolution's decision. Which lifecycle steps may be dispatched as a batch, and the mapping from report items to nodes, are slice design's.

- **Escalations from inside a run are the Runner's main input.** Within a run, Squadron's agents decide and revise on their own; what reaches the Runner is the residue: a checkpoint because a loop did not converge, a flagged batch item, a task the agent marked blocked for a person, a decision CF marks pending. These are the points where the agent was unsure of an outcome or a decision. Before 140, every such point routes to a human, carrying what the agent reported. After 140, the routing table can send the evaluable ones to the Judge first and escalate only what it cannot resolve with consensus. The route is the same table edit either way; nothing in the Runner changes when 140 arrives.

- **Run identity (dependency S9, delivered 20261020).** Squadron now has a public `sq run ... --run-id <id>` (ca9608b0, released in squadron-ai 0.23.5 on 20261020), with a fixed id rule (letters, digits, `.`, `_`, `-`; first character a letter or digit; at most 128). An existing id is refused before anything runs, and every fresh run prints `run_id=<id>` on stderr before its first step. The Runner mints each run's id, journals it, and passes it with `--run-id`, which makes recovery exact: an entry's run is found by id, not matched. Verdict ids are not minted: they are 105's parsed-content digest (evidence contract D5 point 5), the same id detection computes, so recording twice is a retry (slice 125, D7). Because a taken id is refused, a crash between journaling and launch can never produce a second run under the same entry. 100's matching recovery stays only for entries journaled without an id, which means runs from before this change. Note that 100's recovery observer and paused-run pruning both read Squadron's run-state files, which sq-cf calls internal; they move to `sq runs wait --json` (S10), which carries `status`, `paused_at`, and `updated_at`, as part of this work.

- **Observing a run without blocking the tick.** Runs are launched **detached**: in their own session, with stdin from `/dev/null` (100's non-TTY invariant: no implicit resume), and stdout and stderr redirected to per-run log files under the supervisor directory. So a run is never tied to the resident process's pipes or lifetime, and it survives a stop or a crash of the resident process. Observation is by run id, never by process handle: the Runner calls `sq runs wait <id> --timeout 0` for each in-flight run, at most once per tick and no more often than a run poll interval, because each call costs about a second (slice 122, D10). That call reads the run's state once and never sleeps (a pinned Squadron contract since 20261020): exit 4 means still running, and any other code is the outcome. The same call serves runs launched in this lifetime and runs recovery left in flight after a restart (recovery does not resolve an entry whose run exists, so the Runner can still record its review; slice 122, D3), so there are no long-lived wait processes to manage. Liveness is Squadron's to report: a run whose process is gone comes back as `orphaned`, which escalates. The Runner confirms each launch rather than assuming it. It reads the run's log file for the `run_id=<id>` line Squadron prints before the first step. That line is the one deliberate exception to "never read stdout prose": it is part of S9's documented contract (a fixed line format, plain text with no markup, in Squadron's "Launching from another program"), and it is matched exactly, never searched for inside other text. Until that line appears, `not found` means "still launching". If the launch child exits before printing the line, or no line appears within a launch grace period, the Runner polls the id once; if a run state exists, the run is in flight (slice 122, D6). Otherwise the launch failed: the entry resolves failed and the node escalates with the log's tail. After a restart, an entry whose id still has no run state once the launch grace period has passed never started; recovery marks it `not_applied`, and it may be issued again under the same id. A slow launch can still create the run after the grace period. The Runner therefore polls the id again before reissuing, and again if the reissue fails; if the run exists either time, it adopts and observes it rather than failing the entry. This decision rests on the observed run state, never on the error message. The launch grace period is a setting, like the other timing values (see the routing table item). A run that never ends hits a per-pipeline time bound in the table, enforced by the routing engine (slice 125, D12), after which the node escalates; the Runner does not kill runs on its own. Each poll uses `--json` (S10, released in squadron-ai 0.23.5 on 20261020), so one call returns everything:
- `outcome`, mapped one-to-one to the exit code, and the run's own recorded `status`.
- For a pause, a `checkpoint`: kind (`loop_exhausted`, `interactive_checkpoint`, `awaits_human`, `other`), step, whether it is a loop, round and max rounds, the last verdict, the review file behind that verdict, the reason, and when it paused.
- For a failure, a `failure`: kind (`provider_error`, `stall`, `artifact_missing`, `cost_cap`), step, and message.

The review file named there is the one the Runner records and attributes. A null field means unknown, and the Runner treats it as unknown, never as a default.

- **Concurrency is bounded by the working tree.** Two runs that write files in one checkout collide, so a checkout runs one pipeline at a time, and every v1 pipeline counts, since all of them write and commit. The rule is a runnability filter in Decide, keyed on the checkout path CF reports for the node's worktree. A checkout is held from the dispatch's pointer write until its run is no longer running or paused, because a paused run still has its slice branch checked out (slice 125, D4). Other slices in that checkout wait until it is released. Parallel slice work means separate CF worktrees, which is already the PM's practice. In v1, then, a project with one worktree moves one slice at a time, and a paused run stops that project until the PM handles it. "Moves on to other runnable work" means other worktrees and other projects. With S10 the Runner can read why a run paused, so the routing table can send a pause straight to a resolution, for example retrying an exhausted loop within its attempt limit, instead of always to the PM. Which pauses it handles itself is the table's call; the first table still escalates them all. With S12, when the PM does decide, the Runner carries the decision out. Squadron's `max_cost_usd` bounds the spend of each run; a `cost_cap` failure escalates and is never retried automatically. A global limit on in-flight runs across projects waits until real multi-project use shows it is needed.

- **Squadron does the git work; the Runner checks before it dispatches.** Squadron's pipelines commit their own output (`commit_each_iteration`), and its code pipelines enter the slice branch and merge it back into its target, with a merge commit, no push, and a clean abort on conflict. So a successful run leaves a committed tree, and the Runner itself writes nothing to git. The PM works in the same checkouts, so before dispatching any run the Runner observes the tree, and dispatches only if it is clean and on the target or on this node's slice branch. Otherwise the node escalates. The Runner never stashes, resets, or forces anything.

- **Merge policy is a pipeline parameter.** **Merging is a human step by default** ("no merge before code review", merge only on the PM's word). It is a per-project policy, not a fixed rule: for simpler apps and projects the PM can let Amoeba merge a slice into its target after its code review passes (PM, 20261020). The policy lives in static config, defaults to human, and is recorded on each dispatch decision.
  - **Auto-merge:** the Runner dispatches Squadron's P6, which merges.
  - **Human merge:** the Runner dispatches P6 with `-p merge=false` (dependency S11, released in squadron-ai 0.23.5 on 20261020). The run does everything up to the merge, then stops with the slice branch unmerged and checked out. The node waits on a human merge step, and the Runner observes the merge in git (Squadron's own rule: git, not CF's checkboxes, says a slice is merged). The same parameter works on `implement`, P56, P456, and `implement-plan`, so no Amoeba-owned pipeline is needed.
  - Never, under any policy: the Runner merges, deletes branches, or pushes on its own; and nothing merges to `main` when an integration branch is set.

- **Gates come from CF's structured status, and are not trusted alone.** The Runner reads `activeSlice.status` and `gateInfo` through `cf status --json`, never `cf next`'s prose. `pending-decision` is a human step. A CF gate that clears on a `derived` or `imposed` verdict, or on a review whose `standing` is not trustworthy, is still routed on the store's view, not CF's. The two silent-ungate hatches are Tier-1 checks the Runner runs: if either is present, the node escalates; the Runner never writes `review: none`.

- **What the routing table matches on.** Inputs are closed: run outcome, checkpoint kind and whether it is at a loop, failure kind, verdict, standing, inferred tier (after the first proof), finding severity, recurrence (`new` / `recurring` / `gone`), check standing, attempt count, node kind, and lifecycle step. Rules are ordered, first match wins, and the table must end in a catch-all that escalates. **Rule grammar:** a rule is a set of conditions, each naming one input and the values it accepts (one value or a set; an unknown value matches only a condition that names unknown explicitly). It also names one route, plus the route's parameters: attempt limit, and judge-eligible for escalate.

**Where each value lives:**
- **Routing table:** values that decide *what happens*: routes, attempt limits, and per-pipeline time bounds.
- **Settings:** values that govern *how the loop runs*: tick deadline, per-call timeout, and launch grace period.
- **Per-project config:** the merge policy.

The table's file format, and whether projects can override it, are slice design's.

- **Tier-1 predicates are cheap and must be honest.** Field data shows validators that exit 0 having checked nothing and `main` carrying known failures. Every check the Runner runs records what it examined, using 100's check records; a vacuous check is never a pass. The first checks are the ones the first proof needs (ungate hatches, "the validator examined more than zero files"). In v1 a check is a short read-only command or file read, run in Observe under the same per-call timeout and recorded as a 100 check record. Checks are not journaled, because they change nothing. A check that is long or that writes (a test run) will be dispatched the way a run is, once it exists. Baseline-diffed test checks come after the first proof, when its stops show they are needed.

- **Intent is a closed, declarative command set.** Before the Translator exists, the PM steers the Runner by submitting intents directly. The vocabulary is small and structural. A target is a project, an initiative, or a slice. Each target carries two independent settings:
- **Drive:** whether the Runner should advance work under it, and up to which lifecycle step.
- **Hold:** whether the Runner may issue anything new under it. In-flight runs are still observed and ingested while held.

"Pause" sets hold and "resume" removes the target's own hold; they are not events. Hold resolves as "true if any target holds", so a removed hold and a false one behave the same, and only true is stored (slice 124, D5). **Clear** removes a target's own settings so the next one up applies. Applying an intent twice is the same as applying it once, and for one target the later intent in the store's message order replaces the earlier.

The two settings resolve differently:
- **Drive** comes from the nearest target that sets it (the slice, else its initiative, else the project), so a narrow drive overrides a broad one.
- **Hold** is true if any target on the path holds it, so a broad stop always works and cannot be overridden from below.

Example: the project is held and slice 104 is set to resume. Slice 104 stays held, because hold on the project wins. To run only slice 104, the PM clears the project's hold, then holds every other initiative or slice they want stopped. Each target's current desired state lives in its own table, written in the same transaction that acknowledges the intent. Finding the intent that governs a node is therefore a lookup up its path, never a replay of messages. A desired state stays on its node id, and an orphaned node's state has no effect. Applying an intent and acknowledging it happen in one store transaction (the Runner is in-process and the sole writer), so a crash replays nothing. An intent that is already satisfied, meaning the target's settings would not change, is acknowledged as a no-op. A drive to a step the node has passed is applied when it changes the target's settings, because it still stops work beyond that step (slice 124, D5). One the Runner cannot apply is acknowledged with an explicit rejection rather than ignored. This vocabulary is the contract 160 will translate natural language into; 160's command-authority whitelist (OQ5) is a subset of it.

- **Contract changes the Runner needs from 100.** Enforce `done` as terminal in `update_node_status`; add the minted run id to `sq_run`'s parameter keys and make its observer find the run by that id (`sq_run` is already in `REVIEW_PRODUCING_KINDS`, so no registration is needed); give an intent's acknowledgment an outcome (applied, no-op, rejected with a reason) that the submitter can read. That last change is additive: acknowledging is still once per intent, a second acknowledgment still raises, and the Runner never acknowledges twice because apply and acknowledge share a transaction. Add a project-scoped escalation for faults that have no node: a message on the escalation channel with no blocked state, deduplicated on project and fault kind so at most one is open at a time, and closed by the Runner on the first tick where that fault no longer occurs; move 100's recovery observer and paused-run pruning off Squadron's internal run-state files onto its supported surfaces (`sq runs wait --json`, S10); add the routing-decision, table-version, attempt-count, and desired-state tables through the migration mechanism. These changes land as their own slice ahead of the Runner, so the contract changes first and the Runner then codes against it. Node creation from outside the process stays out: the Runner is the only creator of nodes, and outside parts steer it with intents.

- **Do not foreclose programs.** Cross-project dependency edges (180) will make a node in one project wait on a node in another. The decision step therefore reads "is this node's predecessor done?" through one function, so a cross-project predecessor is an added input, not a rewrite.
